# 小影全栈：需求分析与实施方案

分析日期：2026-11-01。本文综合题目正文与四张参考配图，统一说明功能范围、页面布局、技术方案、测试验收和交付要求，作为本项目唯一的总需求分析。本文包含实施前设计；2026-11-03已按该方案开发，实际状态以开发TODO、README与验证记录为准。草案不作为运行证据。

唯一项目根目录：`D:\Files\Java\code\笔试项目\小影全栈`。后续源码、素材、测试、设计、容器配置和交付材料均在此目录组织。

## 1. 题目要实现什么

实现一个独立运行的模板素材制作网站，闭环是：

浏览模板 → 查看要求 → 上传真实图片 → 提交任务并立即取得 ID → Java 后台依次执行三个步骤 → 前端跟踪各任务 → 查看成功结果或失败原因 → 刷新后恢复个人记录和未完成任务。

真正考察的是 Java 多步骤异步处理和前端异步状态管理。无需真实 AI，但上传、受理、后台阶段推进、状态持久化、用户隔离和历史恢复必须是真实实现。不能用前端计时器冒充后台，不能把浏览器 blob URL 当作服务端素材。

题目没有公布分项分值，不自行推测权重。实现复杂度本身不加分，优先做完整、可靠、能解释的闭环。R-14 虽是推荐项，但评估者只在容器内运行项目，建议把 Docker Compose 作为交付基线。

已收到四张试卷截图：图1为模板列表参考，图2/图3为同一制作工作台的不同任务状态，图4为账户设置参考。参考主要布局，正文决定功能边界，不要求逐像素一致。试卷外层的倒计时、水印、滚动答题框和交卷按钮不属于待开发网站。截图显示拍摄时剩余约2天22小时，不能据此推定当前剩余时间或精确截止日期；提交日期仍按原渠道约定。

## 2. 范围与取舍

应完成：分类和模板、详情上传、双端校验、Java 异步任务、三个独立阶段、指定阶段失败、耗时控制、多任务跟踪、查询故障恢复、个人历史、刷新恢复、图片预览、用户隔离、核心测试、CI 和交付文档。

不必实现：真实 AI、支付、会员积分、复杂模板后台、第三方登录、国际化、视频、消息队列集群、结果下载、任务删除、失败任务重新制作、服务重启后自动恢复执行。上传位的素材移除仍是必做。

任务受理幂等、自动重试和断点续跑可讨论取舍，不应挤占核心实现与验证时间。前端防重复点击仍然必做，但它不等于后端幂等。

### 必做与自主选择的边界

题目指定技术栈、核心业务、异步状态、个人记录、关键测试、CI 与交付材料必须落实。线程池、轮询、匿名会话、TanStack Query、表结构和初始化工具是本项目推荐实现，不是题面唯一答案；Docker Compose 为强烈推荐项。

可在不影响核心行为的前提下简化：分类来自种子枚举而非独立表；有限演示数据先不分页；阶段记录放在任务表而非独立 task_step；使用清晰 SQL 初始化替代 Flyway；自写 Hook 替代查询库。简化后仍须保证阶段持久化、多任务隔离、完整恢复、查询清理与竞态处理。

截图中的题外功能不制作无响应的占位入口；个人身份必须在服务端约束记录归属，但不强制邮箱注册或完整密码系统。

## 3. 推荐架构

```text
浏览器 → Next.js：页面、交互、同源接口转发
                 ↓
         Spring Boot：全部业务接口
           ↓                 ↓
         MySQL          有界后台线程池
                             ↓
                  素材检查 → 模拟生成 → 结果整理
                             ↓
                       本地文件数据卷
```

Next.js 不推进任务、不持久化业务。浏览器使用同源 `/api` 转发到 Java，正确转发会话 Cookie、文件上传和错误响应；公共封面公开访问，个人素材与结果通过身份校验接口访问。

### 制作工作台 `/templates/[id]`：对应图2、图3

主布局为左侧约三分之一的制作面板，右侧约三分之二的历史任务区域。比例为从截图提炼的设计建议，并非像素验收条件。桌面两区同屏，小屏上下排列：制作在上、历史在下。

左侧由上到下：返回列表与模板标题 → 示例封面 → 描述和素材要求 → 按数量生成的上传位 → 校验/请求反馈 → 提交按钮。图片可用居中主体加适配背景展示，不必复制原图。

每个上传槽位独立维护 EMPTY、UPLOADING、READY、ERROR；支持选择、预览、替换、移除和上传失败重试。替换时旧响应不能回填，预览对象 URL 及时释放。客户端先校验，Java 再校验；上传未完成或提交中禁用按钮。

右侧标题使用“制作记录”或“历史任务”，展示当前用户任务卡片。建议工作台优先展示当前模板的个人记录，并明确标注“当前模板”；独立历史页查看全部模板记录。该筛选策略属于自主设计，截图不能证明它只展示当前模板。

提交成功后留在工作台，将新任务插入右侧，结束提交 pending；只要素材有效即可继续创建第二个任务，无需等第一个完成。可以保留已上传素材供再次使用，明确提示素材已保留，减少重复上传。

任务卡独立显示：模板/任务摘要、创建时间、等待或处理阶段、失败原因、成功图片。任务失败与查询异常必须使用不同文案与样式。支持手动恢复查询；该操作只重发 GET，不创建新任务。右侧顶部可提供“刷新记录”，与失败任务重新制作明确区分；任务删除图标可以省略。预览成功图可使用对话框。

截图只有 Processing 和 create watermark failed 等简略内容，实现必须补足正文要求的阶段、时间和可理解原因。失败文案可写“结果整理失败（模拟）：无法整理结果文件”，不必实现真实水印，也不必沿用截图的英文错误。

### 全部个人历史 `/history`：补充入口

独立历史页仍可保留，按创建时间倒序展示当前用户所有模板任务，使用与工作台相同的卡片和查询逻辑；不能用它取代配图所示的工作台右侧历史区。

同一 taskId 在两处展示时共用任务实体/查询缓存，不能各有一套冲突的状态。查询键包含 userId、taskId，工作台与全部历史的列表键还应包含筛选条件。离开工作台时取消该页面跟踪，进入历史页从 Java 恢复；Java 后台继续执行。

### 账户入口：对应图4

可用一个轻量身份弹窗显示匿名昵称/用户编号、会话说明和个人历史入口。无需复制邮箱、密码、Reset、账单、订阅政策和删除账户，也无需因此改成完整账户系统。若采用匿名方案，不展示虚假的邮箱或不可用密码设置。

### 状态与基本可用性

加载、空数据、未知模板、上传失败、提交失败、查询失败均有明确反馈。提交超时可能已经受理，应提示先检查历史，不自动盲目重发。

按钮语义正确、焦点可见，上传/替换/移除和图标按钮有标签；结果对话框可用键盘关闭并恢复焦点。深色界面仍要保证文字和状态对比度，不靠颜色单独区分状态。小屏可完成全部主要操作。

## 5. 数据库设计草案

| 表 | 主要字段 | 用途 |
| --- | --- | --- |
| app_user | id、display_name、created_at | 匿名演示用户 |
| user_session | id、user_id、token_hash、expires_at | 服务端会话 |
| template_category | id、name、sort_order | 分类 |
| material_template | id、category_id、title、description、cover_path、required_image_count、accepted_mime_types、max_file_size_bytes、result_fixture_path | 模板和预置结果 |
| asset | id、user_id、storage_path、original_name、mime_type、size_bytes、created_at | 上传素材及归属 |
| production_task | id、user_id、template_id、template_title_snapshot、status、current_stage、failed_stage、error_code、error_message、result_path、simulation_config、version、created_at、started_at、finished_at | 任务状态与配置快照 |
| task_asset | task_id、asset_id、slot_index | 有序输入素材 |
| task_step | task_id、stage、status、started_at、finished_at、error_message | 独立步骤执行记录 |

以上八张表是可解释的完整设计，不是必选表数。类别可用种子枚举；task_step 可改为任务表内的阶段记录，只要独立执行边界和持久化可证明。建议索引：任务 `(user_id, created_at, id)`，素材 `(user_id, id)`；步骤唯一 `(task_id, stage)`，槽位唯一 `(task_id, slot_index)`。

保存模板标题和模拟参数快照，历史不受未来配置修改影响。时间统一 UTC，API 使用含时区的 ISO 8601，前端按本地时区展示。文件实际准备好后才发布成功状态。

建议 Flyway 管理结构与种子迁移，交付可读 SQL，避免同时维护两套初始化逻辑；具体依赖在开工时验证。图片随项目提供并落到后端可访问目录，不依赖远程图片或付费资源。

## 6. 用户身份方案

建议「Java 创建匿名用户 + 服务端随机会话 + HttpOnly Cookie」。不做注册登录，也不直接信任前端传入的 userId。

- 首次访问通过会话接口创建/复用匿名身份，用户和会话持久化至 MySQL；数据库存令牌摘要。
- 刷新依靠同一 Cookie 恢复记录，不能只把历史存在 localStorage。
- 任务查询、历史、素材提交和私人结果访问都检查当前会话归属。
- 普通窗口作为 A，无痕窗口作为 B：两者记录互不可见，B 直接引用 A 的任务或素材 ID 也被拒绝。
- Cookie 丢失、会话过期或换浏览器后无法找回原匿名身份，README 明确此限制。
- 无需额外开发用户切换页面；如果身份失效或变化，前端取消旧请求、清除旧身份缓存，阻止迟到响应回填。

Cookie 设置合理的 SameSite、Path、HttpOnly，生产 HTTPS 使用 Secure；写接口校验来源。个人图片不通过无鉴权静态目录公开暴露。

## 7. API 草案

Java 提供下列业务，同源转发不改变职责。统一错误格式建议 `{code, message, fieldErrors?, requestId?}`。

| 方法与路径 | 输入 | 输出/行为 |
| --- | --- | --- |
| POST /api/session | 无 | 创建或复用匿名会话，设置 Cookie，返回用户摘要 |
| GET /api/me | 会话 | 当前身份；失效 401 |
| GET /api/categories | 无 | 分类数组 |
| GET /api/templates?categoryId=... | 分类可选 | 模板卡片数组 |
| GET /api/templates/{id} | 模板 ID | 详情、类型、数量和大小限制；不存在 404 |
| POST /api/assets | multipart：file、templateId | 201：id、previewUrl、mimeType、sizeBytes |
| POST /api/tasks | templateId、assetIds；demo 配置可选 | 202：已持久化任务快照，至少含 ID |
| GET /api/tasks/{id} | 本人任务 ID | 状态、阶段、结果或错误；只读 |
| GET /api/tasks?templateId=...&cursor=...&limit=... | 会话、可选模板与分页 | items、nextCursor；仅返回本人记录 |
| GET /api/tasks/active | 会话 | 全部未完成任务；避免分页遗漏活动任务 |
| GET /api/assets/{id}/content | 会话 | 本人素材图片 |
| GET /api/tasks/{id}/result | 会话 | 本人成功结果图片 |

任务响应示例：

```json
{
  "id": "task-example",
  "templateId": "demo-postcard",
  "templateTitle": "旅行明信片",
  "status": "RUNNING",
  "currentStage": "GENERATE",
  "failedStage": null,
  "error": null,
  "resultUrl": null,
  "version": 3,
  "createdAt": "2026-11-01T03:00:00Z",
  "finishedAt": null,
  "steps": [
    {"stage": "CHECK_ASSETS", "status": "SUCCEEDED"},
    {"stage": "GENERATE", "status": "RUNNING"},
    {"stage": "PACKAGE_RESULT", "status": "PENDING"}
  ]
}
```

上传校验实际字节数、图片内容与允许格式，不只信扩展名或浏览器 MIME。提交再次检查模板、数量、重复 ID、素材归属、文件可用性及是否符合目标模板要求。后端生成存储路径，不将客户端路径直接用于读写文件。

HTTP 语义：400 参数错误，401 身份失效，404 不存在或无权访问，413 文件过大，415 类型不支持，503 暂不可受理。查询成功返回的任务 FAILED 与查询接口本身请求失败是不同状态。

## 8. Java 异步执行设计

### 状态模型

整体状态：`QUEUED / RUNNING / SUCCEEDED / FAILED`。

阶段：`CHECK_ASSETS / GENERATE / PACKAGE_RESULT`，等待中可为空。阶段记录：`PENDING / RUNNING / SUCCEEDED / FAILED`。

```text
QUEUED → RUNNING(CHECK_ASSETS) → RUNNING(GENERATE)
       → RUNNING(PACKAGE_RESULT) → SUCCEEDED
任何执行步骤失败 → FAILED，停止后续步骤
```

“关闭页面后任务继续”是必做，“重启 Java 后任务继续”不要求；界面上并列多张任务卡也不意味着后端必须并行执行。SUCCEEDED 和 FAILED 是终态，不再回退。失败保存阶段、可理解原因和完成时间，详细堆栈只写日志。查询接口不调用 Worker、不推进流程。

### 受理、事务与调度

1. HTTP 线程完成必要校验，在短事务中创建任务、输入关联和三个待执行步骤。
2. 事务提交成功后再投递 Worker，避免后台线程读取尚未提交的任务。可用 AFTER_COMMIT 事务事件与独立 Worker Bean；避免同 Bean 自调用导致 @Async 不生效。若监听器内还需写库，必须显式进入新的事务/独立事务服务，不能依赖已提交事务的资源继续写入。执行器拒绝的落库同样遵守此边界。
3. 返回 202 与任务 ID，不等待延迟、生成或结果整理。
4. Worker 条件更新 QUEUED → RUNNING；逐阶段落库开始状态、执行模拟操作、落库结束状态。
5. 不用一个大事务包住全流程；sleep 和文件操作在短事务之外，查询才能观察中间阶段。
6. 每步成功才执行下一步，失败落库并立即停止。最后一步完成与任务成功在同一事务提交，结果文件先准备好。
7. 使用有界线程池。演示建议 worker=1、queue=20，容易看到排队；通过配置调节。不使用 CallerRunsPolicy，避免队列满时 HTTP 线程同步制作。
8. 队列拒绝要落库：建议已创建任务置为 FAILED，错误码 QUEUE_REJECTED，阶段为空、注明尚未开始，并返回可查询记录。不能吞异常留下永久等待任务。

### 失败和耗时模拟

仅 demo/test profile 接受可选参数，并验证枚举和耗时范围：

```json
{
  "templateId": "demo-postcard",
  "assetIds": ["asset-a", "asset-b"],
  "simulation": {
    "failAt": "GENERATE",
    "delaysMs": {"CHECK_ASSETS": 1000, "GENERATE": 6000, "PACKAGE_RESULT": 1000}
  }
}
```

failAt 可选 NONE 或三个指定阶段，耗时可限制在 0～30000ms。配置随任务保存，失败在指定阶段开始后、完成前触发；所有后续步骤不执行。默认延迟来自环境配置，正式配置禁止请求任意覆盖。

模拟生成选择模板关联的本地预置图片，整理阶段复制到任务结果目录即可。明确说明结果是演示素材，不声称真实处理了输入；三阶段仍必须有独立执行与状态记录。

### 重启边界

本方案单实例、内存队列，不实现重启后继续执行。已完成状态和文件通过 MySQL/数据卷保留。可选的完善项：启动时将遗留 QUEUED/RUNNING 标记 FAILED，原因 SERVICE_RESTARTED，保留阶段并标记在途步骤中断，避免前端无限等待。这属于中断收尾，不是自动恢复执行。

AFTER_COMMIT 到投递之间进程崩溃仍有窗口；README 如实说明。不要宣称此方案有消息持久化或可直接多实例扩展能力。

## 9. 前端状态与查询生命周期

| 状态域 | 示例 | 隔离单位 |
| --- | --- | --- |
| 上传 | EMPTY、UPLOADING、READY、ERROR | 每个上传槽位和请求代次 |
| 提交 | idle、pending、error | 一次创建请求 |
| 任务业务状态 | QUEUED、RUNNING、SUCCEEDED、FAILED + stage | taskId，以服务端为准 |
| 查询请求状态 | fetching、queryError、lastUpdatedAt | 对应任务的查询 |

推荐查询键 `['task', userId, taskId]`，历史缓存也包含 userId。受理后立即按 ID 合并任务，提交 pending 随响应结束。受理响应本身也可能落后于 Worker 更新，须遵守同样的版本合并规则。详情与历史重叠返回时按 version 接受新快照，不能让迟到响应覆盖终态。

约 1～2 秒轮询即可，优先请求完成后再调度或使用查询库生命周期，避免重叠请求。active 接口也可替换为一次性全量历史（数据规模很小时）或明确的活动任务查询，不强制增加固定路径或分页；关键是恢复完整且每个终态停止自动跟踪。若两个视图共用缓存，按 taskId 去重查询，避免重复定时器。

- 初始化读取 Java 历史和 active 集合，不只跟踪当前历史页的任务。
- 单个任务结束即停止该任务自动查询；无活动任务就无周期轮询。
- 查询异常保留已有任务和最后更新时间，展示恢复按钮，不改写成 FAILED。
- 页面离开取消请求、定时器/订阅，回来后重新恢复；Java 继续执行。
- 身份变化先取消旧查询、清缓存，AbortSignal 或请求代次防止旧用户响应回填。
- 前端定时器只拉状态，不自行切换阶段。

## 11. 核心测试

Java 重点：

1. 精确验证成功步骤顺序和最后可访问结果。
2. 对三个阶段分别注入失败，验证原因、阶段、后续步骤从未调用；后续记录保持 PENDING。
3. 用可控阻塞器证明 Worker 尚未完成时提交已返回，不依赖脆弱毫秒阈值判断异步。
4. 阶段中间状态可查询、查询不执行 Worker、终态重复查询不变。
5. 非法数量、重复素材、他人素材、未知模板、无效文件被拒绝，个人结果也有归属检查。
6. 用真实 MySQL 验证迁移、种子、Mapper、历史与条件更新，不只写 Mock 测试。
7. 队列拒绝有明确终态；若实现重启中断收尾，验证其行为。

测试注入 Sleeper/Clock/阶段执行器，单元测试不真实等待长延迟；MySQL 集成测试可用 Testcontainers 或 CI MySQL service。

前端重点：

1. A/B 并行创建、交错返回，A 成功 B 失败，各自阶段、原因、结果不串。
2. 查询 500/断网不变更业务状态；恢复后继续到终态。
3. A 结束后 A 停轮询 B 继续；全部结束、卸载后无周期请求。
4. 用户切换、分类切换和上传替换后的旧响应不能覆盖新数据。
5. 上传不完整/上传中禁止提交，受理后结束 pending 并允许再创建。
6. 页面从 Java 恢复记录及未完成任务，不以 localStorage 代替后端恢复。
7. 工作台和全部历史共用任务状态，筛选条件清晰，不产生冲突快照或重复轮询；恢复查询仅发送读取请求。

测试验证行为，避免机械复制实现。手工确认桌面左制作右历史、小屏上下可操作、创建A后可以继续创建B、键盘导航、真实上传及结果预览；卡片补齐阶段、时间和原因，不用截图的 Processing 代替正文要求。题目不强制端到端浏览器测试。

## 14. CI、容器与部署回滚

GitHub Actions 对 push 和 pull_request 触发：

- 前端：npm ci → npm run lint → npm run typecheck → npm run test -- --run → npm run build。
- 后端：JDK 21 下 ./mvnw -B verify，包括测试与打包；MySQL 集成测试配置真实数据库环境。
- 建议补镜像构建或 Compose 冒烟，发现路径、权限和初始化问题。

以上是计划命令，后续实际配置 npm scripts、Maven 测试阶段和 Wrapper。不能用 next build 代替 lint。

Compose 包含 frontend、backend、mysql；数据库与文件分别持久化；配置健康检查与依赖启动条件。计划统一入口为 `docker compose up --build`，无需宿主机提前安装 Java/Node 或生成 node_modules、target、.next。

浏览器访问 localhost:3000；Next.js 容器转发到 backend:8080；Java 连接 mysql:3306。不把 Windows 绝对路径写死在容器配置，不用 localhost 指向其他容器。提供无敏感凭据的 .env.example。

部署：准备配置 → 构建固定版本 → 启动并初始化 → 健康检查 → 成功/失败冒烟。回滚：保留上一验收版本和数据库/文件一致备份，停止写入后按兼容性恢复，再启动上一版本验证。默认操作不删除数据卷；down -v 仅用于明确的演示环境清空并注明数据会丢失。

## 17. 常见失分点

- 上传只有 blob 预览，没有后端可用文件。
- 前端假进度，或查询接口推动任务。
- 全流程一个事务，中间阶段对外不可见。
- 创建尚未提交，后台就读取任务。
- 一个 loading/error/result 管全部任务导致串扰。
- 查询失败改成业务失败，旧响应覆盖终态。
- 只跟踪历史第一页，或所有任务结束仍轮询。
- 只在前端按 userId 筛选，后端缺少归属校验。
- 队列满后变成 HTTP 同步执行，或留下永久等待记录。
- Docker 依赖宿主机路径、缺失素材、错误容器地址。
- 文档宣称已完成但没有运行证据，或测试文件存在却未执行。
